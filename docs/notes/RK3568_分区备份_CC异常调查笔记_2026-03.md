# RK3568 分区备份大量 `0xCC` 异常调查笔记

> 整理日期：2026-08-30<br>
> 故障时间范围：2026-03-02 至 2026-03-06<br>
> 板卡/工程：GEC-RK3568b2、RK3568、约 15 GB Samsung eMMC<br>
> 目的：汇总镜像内容、文件时间、哈希、分区表、启动日志及多套瑞芯微工具日志，说明大量 `0xCC` 是怎样产生的，以及它如何影响后续启动和刷机。

## 1. 一句话结论

大量 `0xCC` 的直接来源是**分区导出阶段发生未读取、短读或读取中断后，导出工具仍把未获得真实数据的缓冲区写入了目标镜像**。

这不是设备树自身生成的内容，也不是 eMMC 正常擦除值。正常擦除区域更常见的是 `0x00` 或 `0xFF`；连续、整齐、覆盖整个文件或恰好从 16 MiB 边界开始的 `0xCC`，更符合工具侧预填充/未有效更新缓冲区的特征。

后续又出现了第二个问题：3 月 4 日晚，工具日志记录了多次整套分区写入。时间、分区名和顺序与刚生成的异常备份高度吻合，因此这批坏镜像**很可能又被刷回了设备**，从而把“导出文件损坏”扩大为“eMMC 上多个分区被破坏”。

3 月 5 日 10:50，另一套 RKDevTool v2.84 又成功解包并刷入了一套完整 `update.img`。这次刷写理论上会覆盖并修复 3 月 4 日晚的多数异常内容。但 3 月 5 日下午和 3 月 6 日仍有继续导出、刷写及 USB/Loader 失败操作，因此最终设备状态还受后续操作影响。

## 2. 结论分级

### 2.1 已确认事实

1. `backup\Image\boot.img` 是 32 MiB：前 16 MiB存在真实 FIT 内容，后 16 MiB全部为 `0xCC`。
2. `logo.img`、`oem.img`、`backup.img`、`recovery.img` 和 `userdata.img` 是全文件 `0xCC`。
3. `userdata.img` 长度为 9,047,096,832 字节，其 SHA-256 与等长全 `0xCC` 数据一致。
4. `rootfs.img` 是可识别的 EXT 文件系统，不是全 `0xCC`。
5. `uboot.img` 具有有效 FIT/FDT 头，不是全 `0xCC`。
6. `misc.img` 不是全 `0xCC`；该分区本身允许大量零字节，不能仅凭“多数为零”判坏。
7. 损坏 boot 中的内核横跨 16 MiB 边界，U-Boot 对内核计算出的错误哈希与镜像内容计算结果完全对应。
8. 多套工具日志均出现读取不支持、ReadLBA/ReadFile 失败、USB 错误 31/995/121、设备测试失败等异常。
9. 3 月 4 日 22:36 和 22:53，RKDevTool v2.92 记录了按分区写入 boot、recovery、rootfs、OEM、logo、userdata 等操作。
10. 3 月 5 日 10:50，OECT 目录内的 RKDevTool v2.84 成功写入 GPT 和完整分区集合，操作最终 `ret=1`。
11. `4.19.232驱动backup` 中 boot 的 FDT、kernel、resource 三个 FIT 子镜像 SHA-256 全部与内嵌值一致；用户回忆它们可能由 Linux `dd` 备份，但生成方式尚无独立证据确认。
12. 该目录的 uboot 中，U-Boot、6 段 ATF、OP-TEE 和 U-Boot DTB 共 9 个子镜像 SHA-256 全部匹配，并包含两个逐字节相同的 2 MiB 冗余副本。

### 2.2 高可信推断

1. `0xCC` 是工具侧未被真实设备数据覆盖的占位/初始化缓冲区内容。
2. boot 的第一个 16 MiB读取成功，第二个 16 MiB读取失败、未执行或未正确写回文件。
3. 3 月 4 日晚产生的异常镜像随后很可能被选入 RKDevTool 的分区列表并刷回设备。
4. 错误由“Loader/设备模式不支持稳定读取”和“USB 通信不稳定”共同触发的可能性最高。

### 2.3 当前不能唯一确认

仅凭现有二进制和日志，不能把最底层原因唯一归结为以下某一个：

- AndroidTool v2.38 或 RKDevTool 某版本内部的 16 MiB 分块缺陷；
- 当时下载到 RAM 的 Loader 过旧或与 RK3568/eMMC 不兼容；
- 设备处于 Maskrom 或其他不支持分区读取的状态；
- USB 线、USB 口、Hub、驱动、供电或设备重连造成传输中断；
- 上述问题的组合。
- `4.19.232驱动backup` 两个文件是否确由 `dd` 生成；镜像本身只能证明是完整的原始分区形态，不能唯一识别生成程序。

日志能确认“读取链路失败”，但没有记录每次底层读取命令的完整参数、实际返回字节数、所用 Loader 哈希和源镜像路径，因此无法再细分到唯一实现缺陷。

### 4.2 `C:\rockdev\Image\parameter.txt` 的错误

该文件把 userdata 写成：

```text
-@0x00c38000(userdata:grow)
```

这会让 userdata 从 OEM 的起点开始，覆盖 OEM 和 logo 的地址空间。正确值应为：

```text
-@0x00c80000(userdata:grow)
```

这个 parameter 错误会导致刷机时分区重叠或覆盖，但它**不能解释导出文件为什么整齐地全是 `0xCC`**。它属于另一个独立风险：导出侧产生坏文件，错误 parameter 又可能在写回时扩大破坏范围。

## 6. 各镜像内容取证

### 6.1 boot：典型的 16 MiB 短读/未填充边界

`backup\Image\boot.img`：

- 文件总长：33,554,432 字节，即 32 MiB；
- 文件开头：`D0 0D FE ED`，是有效 FIT/FDT 魔数；
- 偏移 `0x01000000`，即 16 MiB之后，全部为 `0xCC`；
- 后半段长度恰好也是 16 MiB，即 `0x8000` 个 512 字节扇区。

这非常像一次按 16 MiB 分块的读取：第一块成功，第二块失败或未执行，工具仍保存了完整 32 MiB 文件。

### 6.2 全 CC 分区

以下镜像的 SHA-256 与对应长度的全 `0xCC` 数据一致：

| 文件 | 长度 | SHA-256 |
|---|---:|---|
| logo.img | 16 MiB | `EA07B7498CB65606B02F9C1214534FD1AA218634CF86C0B9E55A335999352C37` |
| backup.img | 32 MiB | `313901D3C6DA358C92DEE4AEBE19A3D831FB8922E38CCBC12E1095F53DA5A178` |
| recovery.img | 32 MiB | `313901D3C6DA358C92DEE4AEBE19A3D831FB8922E38CCBC12E1095F53DA5A178` |
| oem.img | 128 MiB | `727C1AE83A3955121D8830C8C95D64B3791CD3C285BA8D9867BC1E623ADBDD2D` |
| userdata.img | 9,047,096,832 B | `600A61A0588390EDF55383AE1BB4DEC807D0BE407E68F989891E9B2FFAFA4546` |

backup 和 recovery 哈希完全相同不是因为它们原始数据相同，而是因为二者长度同为 32 MiB，并且都完全由 `0xCC` 构成。

### 6.3 misc

misc 的 SHA-256 为：

```text
BB000DDEECF06C7899AAFE54581918E7E77586D69988200A262315EF3760E625
```

它既不等于 4 MiB全零数据，也不等于 4 MiB全 `0xCC` 数据，因此不能归入这批全 CC 坏镜像。misc 分区通常保存启动控制、recovery 命令等少量状态，大面积为零并不异常。

### 6.4 设备树问题

`0xCC` 不是可用设备树。有效 FDT/DTB 至少应以：

```text
D0 0D FE ED
```

开头，并包含合法头部、结构块和字符串块。如果 DTB 所在范围被 `0xCC` 覆盖，该 DTB 完全不可解析。

不过本次 boot 的首要失败不是单纯“设备树没用”，而是 FIT 中 21.2 MiB 的内核本体已经跨越 16 MiB 边界，U-Boot 在加载设备树之前或同时进行的内核哈希校验就已经失败。

## 7. boot 哈希失败与启动日志的直接对应

坏板启动日志记录：

```text
Data Size:    22267912 Bytes = 21.2 MiB
Hash value:   1792bf23cc6f42784157b9740f29f1b41d195676a166de29003a12a3b9df71b3
Verifying Hash Integrity ... sha256 Bad hash:
4a8973798784694acb6ef8346badd16b4e6b9bb76e91e5eea1ac2247c4428551
Bad Data Hash
ERROR: can't get kernel image!
```

FIT 中内核数据相对 boot 文件起点约从 `0x22200` 开始，长度为 22,267,912 字节，结束位置约为：

```text
0x155EA08
```

也就是内核数据有 5,630,472 字节落在 16 MiB边界之后。后半段被 `0xCC` 替代后，内核不可能通过原始 SHA-256 校验。

对截断/CC 尾部 boot 中的内核数据重新计算，得到的错误值正是：

```text
4a8973798784694acb6ef8346badd16b4e6b9bb76e91e5eea1ac2247c4428551
```

因此日志中的 `Bad hash` 与 boot 文件后半段 `0xCC` 之间不是猜测，而是可以一一复现的直接因果关系。

## 13. USB 错误码的含义

这些错误码不能单独指出哪根线或哪个 Loader 有问题，但能证明传输链路异常：

| 错误 | 常见含义 | 本案影响 |
|---|---|---|
| 995 | I/O 操作被中止 | 设备断开、请求取消、驱动重置时常见 |
| 121 | 信号灯超时/设备未在规定时间响应 | USB 控制请求超时、设备无响应 |
| 31 | 连接到系统的设备没有发挥作用 | 设备状态异常、端点/驱动操作失败 |
| `err=-3/-4` | 工具内部读写/设备操作失败 | ReadLBA、FlashInfo、Capability、Reset 等失败 |
| `device did not support to read` | 当前设备模式/Loader声明不支持读取 | 无法可靠执行分区导出 |

`RKU_Write-->WriteFile failed` 中的 “WriteFile” 是 Windows 对 USB 设备句柄发命令失败，不等价于“向本地镜像文件写入失败”。但它证明工具和设备之间的 USB 命令传输失败。

## 15. 最可能的故障机制

### 15.1 直接机制

```text
工具按分区长度创建目标文件
        ↓
为读缓冲区保留/填入固定模式 0xCC
        ↓
向设备发出 ReadLBA/读取命令
        ↓
设备模式不支持读取，或 USB/Loader 请求失败、短读
        ↓
缓冲区没有被真实 eMMC 数据完整覆盖
        ↓
工具仍将缓冲区写入文件，并保留正常分区尺寸
        ↓
得到“大小正确、内容全 CC或部分 CC”的假备份
```

### 15.2 为什么有的分区正常、有的全 CC

- uboot、misc 较小，可能在连接短暂正常时一次读取完成；
- rootfs 可能由另一次连接、另一个工具进程或多次操作完成；
- logo、OEM、backup、recovery 在各自操作中没有获得有效数据；
- boot 第一块 16 MiB成功，第二块失败；
- userdata 在紧邻 ReadLBA/USB 失败之后导出，整段没有获得真实数据。

### 15.3 为什么不是设备树导致

设备树只影响内核如何识别硬件、驱动和资源。设备树写错可能导致外设不工作、内核启动失败或硬件冲突，但不会让 Windows 上的导出程序把整个 16 MiB、32 MiB、128 MiB、8.43 GiB文件整齐写成同一个 `0xCC` 字节。

### 15.4 为什么不是 parameter 单独导致

parameter 决定分区地址和大小。地址错误会导致读错区域或刷写覆盖，但不能自然产生恰好一致的全 `0xCC` 哈希。它能解释“写错位置/覆盖”，不能单独解释“导出缓冲区未被真实数据覆盖”。

## 16. 对此前问题的集中回答

### “为什么这些分区都是 CC？”

因为导出时读取没有成功，工具仍生成了完整尺寸文件，并把未获得真实数据的区域保存为 `0xCC`。

### “boot 为什么 16 MiB之后都是 CC？”

32 MiB boot 很可能按两个 16 MiB块读取。第一个块成功，第二个块失败或未执行；16 MiB正好是 `0x8000` 个扇区。该边界在不同板子的两次导出中重复出现，强烈指向工具/Loader/传输链路，而不是单块板的存储内容。

### “0xCC 设备树完全没用吗？”

全 `0xCC` 不是合法 DTB；如果设备树数据区被覆盖就完全不可用。但这份 boot 连内核本体都被 `0xCC` 污染，首先触发的是内核 SHA-256 校验失败。

### “C:\rockdev\Image 和 backup 有几部分完全相同？”

当前 SHA-256 重算结果为 7 个文件完全相同：MiniLoader、misc、recovery、backup、rootfs、OEM、logo。其中 6 个是分区镜像。boot、uboot、parameter 不同。

### “hash 比对了吗？”

已比对。完全相同的判断来自 SHA-256，不只是文件大小或时间；全 CC 的判断也通过全文件哈希与理论全 `0xCC` 数据核对。

### “日志里的 ReadFile failed、短读、USB 995/121 体现在哪里？”

- v2.92：3 月 3 至 6 日反复出现 ExportImage 不支持、ReadLBA、995、121、31；
- v2.84：3 月 3 日同样出现不支持读取及 31/995；
- v2.38：3 月 5 日出现 `RKU_Read ReadFile failed, read=0`，3 月 5 至 6 日继续出现 31/995/121 和 ReadFlashInfo 失败。

这些日志证明读取环境不稳定，但没有记录“第二个 16 MiB读取块具体在哪一条命令失败”，因此不能只凭日志锁定唯一软件缺陷。

```text
p3 boot     起点 0x00008000，长度 0x00010000 扇区
p4 recovery 起点 0x00018000
p5 backup   起点 0x00028000
p6 rootfs   起点 0x00038000
p7 oem      起点 0x00c38000
p8 logo     起点 0x00c78000
p9 userdata 起点 0x00c80000
```

因此聊天中的以下示例不能直接用于本板：

| 聊天示例 | 本板实际含义/风险 |
|---|---|
| `dd if=/dev/mmcblk0p6 ...boot_fix.img` | p6 实际是 rootfs，不是 boot；boot 是 p3 |
| `root=/dev/mmcblk0p7` | p7 实际是 OEM，不是 rootfs；rootfs 是 p6 |
| `mmc write ... 0x100000 0x10000` | `0x100000` 落在 rootfs 内，不是 boot 起点；boot 起点是 `0x8000` |
| “`0x400000` 扇区 = 1024 MiB” | 计算错误；512 字节扇区下 `0x400000` 是 2 GiB，1 GiB应为 `0x200000` 扇区 |
| 写整个 eMMC 前 1 GiB | 会覆盖 GPT、uboot、misc、boot、recovery、backup 及部分 rootfs，风险远高于只修复 boot |

若实际执行了 `mmc write 0x70000000 0 0x400000`，而内存中只通过 TFTP 加载了 1 GiB文件，命令还会继续读取并写入文件末尾之后约 1 GiB的内存内容，属于严重破坏风险。

修复本板 boot 时，只有在再次核对 `mmc part` 与 GPT 一致后，原始扇区参数才应是：

```text
boot 起始 LBA = 0x8000
boot 分区长度  = 0x10000 扇区 = 32 MiB
```

即使地址正确，也应优先使用有分区名校验和读回哈希验证的流程，不应盲目照抄示例地址。

## 19. 最终判断

本次问题不是单一“设备树错了”或单一“parameter 地址错了”，而是一条连续故障链：

```text
Loader/设备读取能力异常 + USB 通信不稳定
                ↓
分区导出失败或短读
                ↓
RKDevTool/AndroidTool 未正确丢弃失败结果
                ↓
生成全 CC或部分 CC 的假备份
                ↓
坏 boot 内核跨过 16 MiB边界，SHA-256 校验失败
                ↓
异常镜像很可能又被按分区刷回
                ↓
boot、recovery、OEM、logo、userdata 等内容被破坏
```

现有证据足以确认“CC 在导出失败时形成”和“CC boot 直接导致内核 Bad hash”；也足以高度怀疑 3 月 4 日晚坏镜像被刷回。现有日志不足以唯一判定是 v2.38 内部 bug、旧 Loader 还是具体 USB 硬件中断，但这不影响对坏镜像本身和启动失败原因的判断。
